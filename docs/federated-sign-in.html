Third-party sign-in

An operator can let people sign in to their vlPDS account with an account they hold somewhere else: Google, Apple, a company identity provider, or a wallet through an adapter. vlPDS speaks one protocol to all of them, OpenID Connect, and has no provider built in. A provider sign-in is one more way past the password step. The account's own second factors still apply, email stays required, and an identity is never matched by its email.

Status: design for review. Nothing here is built yet. P1 is sign-in and linking for existing accounts, P2 is signup with a provider identity, P3 is SIWE and other non-OIDC methods through an adapter.

Decisions

Email stays required for every account, provider signups included, because moderation runs on it.

A provider sign-in does not replace the account's second factor. An account with TOTP, passkeys or the email factor still gets that step after the provider says yes.

vlPDS speaks only OIDC. Sign-In with Ethereum, GitHub, Discord or anything custom comes through an OIDC adapter the operator runs (Dex, Authentik, Keycloak, siwe-oidc and the like). None of them is built in.

From those three, the rest of the design follows a few rules. One generic OIDC relying party with every provider as config. An identity is the issuer plus the subject from a validated id_token, held cluster-wide by a claim object. The flow's state is bound to the browser that started it. Linking takes a fresh sign-in on that browser. An account always keeps at least one way in. The whole feature waits for a feature level.

Architecture

The new code is one module (src/federated/) plus small hooks in the OAuth pages, the sign-in log and the session checks. It doesn't add a session kind. A provider sign-in ends in the same device sign-in and the same tokens a password does, with one more credential reference on them.

Secrets never sit in the object in the clear. The admin API takes a plaintext value and stores it wrapped under the KEK (new purpose sign-in-provider-secret, subject the provider id). There is no file form: an admin API that names files would let any operator login read a file on the node and post it to a token endpoint of its choosing. The list call says a secret is stored, never its value. rewrapSecrets rewraps them with the rest.

Admin surface: vlpds.admin.listSignInProviders, putSignInProvider (create or replace, ifVersion), removeSignInProvider, the CLI's vlpds admin signin-provider list|put|remove and a console page. Saves and removals are audited (signin_provider.put, signin_provider.remove).

The sign-in

  • Bound to the browser. The state row records the device id of the cookie that started the flow, and the callback refuses any other. A link an attacker started can't finish in someone else's browser, which closes login CSRF.
  • Nothing secret in the row. The nonce and the PKCE verifier are HMACs of the state under a key derived from jwt_secret, so any node recomputes them and a copy of the bucket gives neither. The row holds what the callback needs to check and where to go next.
  • Used once. The callback deletes the row with a conditional write before it calls the token endpoint, so a replayed callback or handoff gets "already used". The OAuth request it continues gets the same 10 minutes, since the provider's own sign-in can take longer than the page's usual 5.
  • Identity only from the id_token. There is no userinfo fallback. A failed check ends the sign-in.
  • The account's factors. After the identity resolves, the sign-in continues exactly where a correct password would: a trusted browser skips the second step, otherwise TOTP, a passkey, a recovery code or the email code. Lockouts, the sign-in log and new-device alerts are the existing ones.
  • Unknown identity. P1 says no account uses this identity and points to signing in another way and adding it. It never looks for an account with the same email. P2 offers signup when the provider allows it.

The same buttons appear on /oauth/account (the device's account page). The account page app at /account gets them in P2, when accounts without a password appear.

Discovery ({issuer}/.well-known/openid-configuration), the JWKS and the token endpoint go through the SSRF-guarded client, unless the issuer itself is a non-public address (an adapter on the operator's network), whose endpoints are then fetched as configured. Plain http only to a loopback issuer or in dev mode. Fetches are single-flight per URL and a failure is remembered for 10 s. Both are cached for an hour (a failed refresh keeps the last good copy for a day), capped at 256 KiB, with 10 s deadlines. email_verified is accepted as a boolean or the strings "true"/"false", since some providers send strings.

Linking and unlinking

Where. Adding and removing happen on /oauth/account, the server-rendered page tied to the browser's device cookie, never through a bearer-token API. A fresh sign-in there (password with its second factor, a passkey, or an identity already linked, within the last 10 minutes on this browser) is the step-up, so a stolen account-page token can't add a way into the account. The account page app's Security tab lists the identities (vlpds.server.listFederatedIdentities) and sends the user to /oauth/account?login_hint=did&return=sign-in-methods to change them. The app's own session doesn't count as that sign-in, so without a fresh one on this browser the page asks for it ("Confirm it's you", the handle filled in, every way to sign in offered; signing in adds the account if the browser is signed in to another), then lands on the account's sign-in methods. The hint is used only if it is the DID of an active account here (its own handle is shown; a handle hint is ignored), and return takes only that one value. Add is a GET link carrying a CSRF token with its issue time, good for the same 10 minutes (a POST would trip form-action on the redirect to the provider), and it asks the provider to let the user pick an account (prompt=select_account), so a link never silently takes whichever account the browser is signed in to there. Remove is a form post.

Limits. 10 identities per account, one per issuer. Linking is rate-limited per account (federated-link-account, 10 a day). Every add and remove mails the owner ("Your Account's Sign-in Settings Changed").

Never by email. An identity is linked only by someone already signed in to the account. Its email is kept as a label for the list and nothing else, and later sign-ins don't update the account's email.

Storage

The identity hash is SHA-256 over the issuer, a zero byte and the subject, so two issuers can't collide on a subject and the object name says nothing about who the user is. The credential reference on sessions is the first 12 bytes of that hash, the same size as a passkey's pk: reference. When a passkey is the second factor after a provider sign-in, the session records both (fed:… pk:…), and removing either ends it.

An unlink racing a sign-in is safe the way a passkey removal is: the removal writes the row before it scans for sessions, and a sign-in checks the row again after it writes its session, so one of them sees the other.

Signup with a provider P2

  • The internal create path takes no password; public createAccount still requires one. Such an account has an empty password hash, which every build's password check already refuses.
  • Email is required. With trustEmail and email_verified the form is prefilled and the address is marked confirmed. The email policy (disposable domains) and uniqueness apply either way.
  • Invites follow the provider's policy (invite needs one, open doesn't) and --invite-required still applies on top.
  • The ambiguous-outcome check in account creation compares the password hash today, which an account without a password doesn't have. It compares the signing public key instead: a fresh key per request, already on the account, so the per-create nonce costs no new field.
  • The account page app gets provider buttons too. The provider sign-in runs on the server pages (second factor included), and a one-time, device-bound handoff gives the app a session (vlpds.server.createFederatedSession), so tokens never ride in a URL. It's the full account-page session createSession gives this server's own page, so the OAuth-only switch doesn't apply to it, as it doesn't to the page's password sign-in.
  • Each provider makes at most signupsPerDay accounts a UTC day (default 100, 0 for no cap), counted cluster-wide, on top of the per-IP create-account limit.

SIWE and other non-OIDC methods P3

No code in vlPDS knows what a wallet is. The operator guide covers running an adapter in front of a non-OIDC method, what its subject should be (stable, never reassigned) and which response mode to pick. An interop test drives a mock SIWE adapter end to end: a wallet key signs a SIWE message, the adapter checks it and issues an id_token, and vlPDS signs in the linked account. The identity key is still the adapter's issuer plus its subject, so changing adapters or issuer URLs strands identities, and the guide says so.

Feature level 2

Why a level and not only a flag: an old build doesn't know fed: credential references or the fedid row, so a mixed cluster could sign someone in on a new node and then let an old node keep a session that an unlink should have ended. A level keeps those bytes from existing until no old build can run. It is persistent because the claims, rows and references live in the bucket. Old builds fail safe anyway: they never read the config object, an empty password hash never verifies, and an unknown credential reference reads as "removed", so their device sign-ins drop. The level makes that a guarantee instead of a property of today's code.

This is the first real level after baseline, so it also moves the test-only level to 3 and records testdata/formats/L2. The level-2 fixtures freeze with the first release that has it.

Recovery

  • No password (P2 accounts). The email reset works as "set a password". A user who loses the provider account and the inbox needs the operator, as with a lost password and inbox today.
  • Own your identity. The docs recommend a user-held PLC rotation key (the Security tab already adds one), so a user can move the account even if this PDS or a provider goes away.
  • A provider removed. Its identities go dormant: no button, no sign-in, still listed and removable. Adding a provider with the same issuer brings them back. Accounts that only had that provider recover through the email reset.
  • Apple specifics, in the operator guide. A user may share a private relay address, and mail to it is delivered only after the operator registers the sending domain with Apple. Apple sends the user's name only on the first authorization, so vlPDS never depends on it.

Not now

  • Built-in SIWE, GitHub or any non-OIDC method. Adapters cover them.
  • Userinfo. Display claims come from the id_token; a userinfo call would only add display data, and only with the same sub.
  • Operator-side unlink and a per-account identity view in the console beyond the list.
  • Front- or back-channel logout from providers. A provider sign-out doesn't end vlPDS sessions, as with any password manager's autofill.
  • Encrypted id_tokens (JWE) and request objects to providers.
  • A provider step-up for what asks for the password: an account made with a provider sets a password by the email reset before it can delete itself, remove a passkey or reactivate after deactivating.
  • An option to end the sessions a provider signed in when the operator removes it. Today its identities go dormant and their sessions run out on their own.
