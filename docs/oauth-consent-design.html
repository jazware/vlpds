OAuth consent and connected apps

Apps like Streamplace ask for the same permissions twice, once as scopes and once through a permission set. vlPDS shows both, gives each scope its own checkbox, and dumps the set as a wall of NSIDs. Most of those checkboxes change nothing. This design shows every effective permission once, in a few rows sorted by what's at stake, and gives a checkbox only where unticking it takes something away.

Status: design for review. Mockups first, nothing here is built yet except the one-line CSS fix for the connected-apps table (below). Test data is Streamplace's public client metadata and its place.stream.authFull permission set as published on 2026-11-25.

Partial grants stay, at row granularity. The OAuth spec lets the user refine granular scopes and requires the granted scope in the token response. Per-scope checkboxes fail because grants are additive: a checkbox under a set that covers it can't take anything away. Per-row checkboxes always can. Per-collection choice inside an app is gone. Nobody can judge place.stream.media.viewCount alone, and apps break on half a namespace.

Current state

  1. 1The set's row is a sentence listing all 28 NSIDs, then the same 28 again as a list. Nothing is grouped or named.
  2. 2The same 28 collections show up a third time in the collapsed place.stream group at the bottom, each with a checkbox. Unticking one leaves the app able to write it through the set.
  3. 3The set's own checkbox also does nothing today: the inline scopes cover all 28 collections. It only removes what stream.place might add to the set later.
  4. 4Order is request order. Uploads of any file type sit above the Bluesky group. Reports to any service read as "Make requests on your behalf to any service".

Connected apps

Both screens show scope strings to people who don't read them. The consent screen at least groups and names the inline scopes. The account page shows nothing but raw strings, and include: scopes there say nothing about what they grant.

The permission model

atproto permissions are additive. A token's scope is a list, a request is allowed when any entry in it matches, and there is no negative entry. A permission set is one more entry: the PDS resolves it to its repo and rpc permissions and the union decides. That is why the checkboxes in issue #16 are meaningless. Unticking one source of a permission leaves the other.

Where the spec is silent.
  1. Whether a server may refuse part of a set. This design never does: a row drops an include: whole, and never rewrites it into the inline scopes it would have granted, since the client didn't request those strings and would lose the set's updates.
  2. Whether a refused row should be asked for again. A confidential client that asks for the same scopes next time gets the consent screen again, since the refused scopes aren't in the stored authorization. That is today's behavior and stays.
  3. Whether a set can be trusted to describe itself. Its title and detail come from the NSID's DNS-verified publisher, not from the client, so the screen shows them. A client can include another publisher's set, and the chip then names that publisher's set accurately.
  4. What the token response's scope holds for a set. vlPDS returns the expanded permissions, not the include:. Out of scope here, noted for a later look.

"Matching the client's host" compares the client_id host, read right to left, with the NSID authority. The client's host is real (the PDS fetched its metadata there) and the NSID authority is DNS-verified. It uses the public suffix list, so someone.github.io doesn't own io.github.*.
